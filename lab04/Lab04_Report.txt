1. The Deadlock (Phase 2):
ในสคริปต์ `deadlock_simulation.py` สภาวะ "Circular Wait" (การรอคอยเป็นวงกลม) เกิดขึ้นจากการที่ Model A ทำการจอง (Lock) GPU 0 สำเร็จและกำลังรอ GPU 1 ในขณะเดียวกัน Model B ก็จอง GPU 1 สำเร็จและกำลังรอ GPU 0 ทำให้ต่างฝ่ายต่างรอทรัพยากรที่อีกฝ่ายถือครองอยู่ ระบบจึงหยุดชะงัก (Freeze)

2. The Solution (Phase 3):
การแก้โค้ดใน `deadlock_avoidance.py` โดยบังคับให้ Model B ต้องขอ GPU 0 ก่อน GPU 1 เป็นการทำลายเงื่อนไข "Circular Wait" (การจัดลำดับชั้นทรัพยากร หรือ Lock Ordering) เพราะทั้งสอง Model จะต้องมาต่อคิวแย่ง GPU 0 ก่อนเสมอ ใครที่ได้ GPU 0 ไปก็จะสามารถไปขอ GPU 1 ต่อได้จนจบงาน ส่วนอีกตัวก็ต้องรอจนกว่าตัวแรกจะทำงานเสร็จ ทำให้ทิศทางการรอคอยเป็นเส้นตรง ไม่ไขว้กันเป็นวงกลม

3. Starvation vs Deadlock (Phase 4): 
- ความแตกต่าง: ในสคริปต์ Deadlock (Phase 2) ระบบโดยรวมจะค้างและไม่มีโปรแกรมไหนทำงานต่อได้เลย แต่ในสคริปต์ Starvation ระบบยังคงรันต่อไปได้ เพียงแต่มีบางโปรแกรม (Polite_Model) ที่ถูกโปรแกรมอื่นที่จองทรัพยากรถี่กว่า (Greedy_Model) แย่งชิงทรัพยากรไปหมดจนแทบไม่ได้ทำงาน
- การใช้ Aging: OS Process Scheduler สามารถใช้เทคนิค "Aging" เข้ามาแก้ปัญหา Starvation ได้ โดยระบบจะค่อยๆ เพิ่มระดับความสำคัญ (Priority) ให้กับโปรแกรม Polite_Model ที่รอนานๆ เมื่อความสำคัญสูงถึงจุดหนึ่ง OS จะบังคับให้สิทธิ์ Polite_Model ได้เข้าไปใช้ CPU ก่อนพวก Greedy Model ทำให้ได้รับการแบ่งปันเวลาอย่างยุติธรรม

4. Deadlock Detection & Recovery (Phase 5):
- การจำลอง OS Detection: พารามิเตอร์ `timeout=2.0` เป็นกลไกที่จำลองการเฝ้าระวังของ OS โดยหากโปรแกรมร้องขอทรัพยากรและต้องรอนานเกินขีดจำกัดที่กำหนด (2 วินาที) OS จะถือว่าเกิดภาวะ Deadlock ขึ้นในระบบ
- การทำ Recovery: เมื่อตรวจพบ Deadlock สิ่งที่ Model A ทำเพื่อฟื้นฟูระบบคือการยอมสละ (Release / Rollback) ทรัพยากร GPU 0 ที่ตนเองถือครองอยู่ออกมา เพื่อเปิดทางให้ Model B สามารถนำ GPU 0 ไปใช้และทำงานให้เสร็จสิ้น ระบบจึงหลุดจากภาวะค้างได้
